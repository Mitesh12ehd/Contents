Module 0 - How to use this guide

0.1 Why this order

Your list put EC2 Scaling first and Load Balancing second. This guide teaches load balancing first, then Auto Scaling, then the combination. Reasons:

  • Auto Scaling health checks, dynamic registration, and the request count scaling metric all depend on target groups and load balancer health checks. Without those concepts, half of Auto Scaling looks abstract.
  • In real life, an ALB plus a fixed pair of EC2 instances is a valid first architecture. Auto Scaling is added on top.
  • Every topic from both of your lists is covered. Topics that appear in both lists (Auto Scaling + ALB, health checks) are taught once in depth and cross-referenced.

0.2 Structure of each topic

  • Concept - what it is and why it exists.
  • How it works - mechanics and important settings with default values.
  • Production importance - Critical, High, Medium, or Low. Critical means a wrong setting commonly causes outages in live environments.
  • Take care in live - things to configure or watch in production.
  • Common live issue - a real-world failure pattern, its cause, and the fix.

0.4 Lab setup

  • Use a personal AWS account, not a work account. Use a region close to you (examples use ap-south-1, Mumbai).
  • Run CLI commands in AWS CloudShell (bash). The commands in this guide use bash quoting. PowerShell quoting of JSON is different and is a common source of errors.
  • VPC for labs: one VPC, 2 public subnets in 2 different Availability Zones (AZs), and 2 private subnets in the same 2 AZs. For cheap labs you may put EC2 in public subnets with public IPs to avoid NAT Gateway cost. In production, EC2 goes in private subnets.
  • Create an IAM role for EC2 named web-ec2-role with the managed policies AmazonSSMManagedInstanceCore and CloudWatchAgentServerPolicy. Use Session Manager instead of SSH keys.
  • Two security groups:
    • alb-sg: inbound 80 and 443 from 0.0.0.0/0.
    • web-sg: inbound 80 only from alb-sg (source is the security group, not a CIDR).

Standard user data script used across labs (Amazon Linux 2023). It serves a page showing instance ID and AZ, plus a /health endpoint:

0.5 Cost warning

  • ALB and NLB charge per hour plus per capacity unit even with zero traffic (roughly USD 0.02 to 0.03 per hour plus usage, varies by region).
  • NAT Gateway charges per hour plus per GB. It is often the most expensive item in a lab.
  • Auto Scaling itself is free. You pay for the EC2 instances, EBS volumes, and CloudWatch detailed monitoring and alarms.
  • Set a billing alarm or AWS Budget before starting. Run the cleanup in the Appendix at the end of each lab day.

Module 1 - Foundations

1.1 Vertical vs horizontal scaling

  • Vertical scaling (scale up): bigger instance type, for example t3.medium to m6i.xlarge. Needs a stop/start, has an upper limit, and the single instance is still a single point of failure.
  • Horizontal scaling (scale out): more instances of the same type. No hard limit, survives the loss of an instance, but requires the application to be stateless and requires something to distribute traffic. That something is the load balancer. Something has to add and remove instances. That is Auto Scaling.

1.2 High availability vs scalability vs elasticity

  • High availability: the service survives failure of an instance or a whole AZ. Achieved by running in at least 2 AZs.
  • Scalability: the system can handle more load by adding resources.
  • Elasticity: resources are added and removed automatically to match demand, so you pay only for what you need.

1.3 Stateless application design (Production importance: Critical)

Auto Scaling will terminate instances at any time (scale in, health replacement, instance refresh, Spot interruption). Anything stored only on the instance is lost.

  • Sessions: store in ElastiCache (Redis/Valkey), DynamoDB, or signed tokens (JWT). Avoid relying on sticky sessions as the only mechanism.
  • Uploaded files: store in S3, not local disk.
  • Logs: ship to CloudWatch Logs or another central system. Local logs vanish on termination, which removes the evidence you need for post-incident analysis.
  • Configuration: pull from SSM Parameter Store or Secrets Manager at boot, not baked into a single hand-edited server.
  • Cron jobs: do not run them on every web instance. Use EventBridge Scheduler, a separate worker, or a leader-election mechanism.

Common live issue: a team migrates a legacy app behind an ALB with 2 instances. Users get logged out randomly. Cause: sessions in local memory. Quick fix: enable stickiness. Real fix: move sessions to Redis.

Module 2 - Load Balancing + EC2

2.1 Why a load balancer?

Concept: a load balancer is a single stable endpoint (DNS name) that receives client traffic and spreads it across multiple backend targets.

What it gives you:

  • Traffic distribution across many instances, so no single instance is overloaded.
  • Health checking: traffic goes only to healthy targets. Failed instances are bypassed automatically.
  • High availability across AZs.
  • A stable endpoint: instances come and go, but clients keep using the same DNS name.
  • TLS termination in one place (certificates managed centrally with ACM).
  • Security boundary: instances can sit in private subnets with no public IPs; only the load balancer is internet facing.
  • Layer 7 routing (ALB): send /api to one service and /images to another, route by host name, etc.
  • Integration with WAF, Shield, access logs, and CloudWatch metrics.

Without a load balancer, you would need DNS round robin (slow failover because of DNS caching, no health awareness) or a self-managed proxy such as HAProxy (which you would then need to make highly available yourself).

2.3 Application Load Balancer (ALB) - Production importance: Critical

Building blocks:

  • Load balancer: internet-facing (public subnets) or internal (private subnets). Must have subnets in at least 2 AZs. Has its own security group.
  • Listener: a protocol and port the ALB accepts, for example HTTP 80 and HTTPS 443.
  • Rules: evaluated in priority order on each listener. Conditions can match host header, path, HTTP method, HTTP headers, query string, and source IP.
  • Actions: forward (to one or more weighted target groups), redirect (for example HTTP to HTTPS), fixed response (for example a maintenance page), authenticate (Cognito or OIDC).
  • Target groups: the backend pools (section 2.6).

Important behaviours:

  • The ALB terminates the client connection and opens a new connection to the target. The target sees the ALB's private IP as the source. The real client IP is in the X-Forwarded-For header; the original protocol is in X-Forwarded-Proto.
  • The ALB's IP addresses change over time. Always use the DNS name (Route 53 alias record), never hard-code IPs. If a client needs static IPs, put an NLB in front of the ALB (ALB as NLB target) or use Global Accelerator.
  • Idle timeout default is 60 seconds. If no data is sent for that long, the ALB closes the connection.
  • Routing algorithms per target group: round robin (default), least outstanding requests, weighted random (optionally with automatic target weights / anomaly mitigation).
  • The ALB scales itself automatically, but scales gradually. For a known huge spike (product launch, sale event), use the LCU capacity reservation feature or contact AWS Support beforehand.
  • Pricing: hourly plus Load Balancer Capacity Units (LCU), based on new connections, active connections, processed bytes, and rule evaluations.

Take care in live:

  • Enable access logs to S3 and connection logs if needed. They are disabled by default, and you will want them during the first incident.
  • Enable deletion protection.
  • Attach AWS WAF for internet-facing ALBs (rate limiting, managed rule groups).
  • Set the "drop invalid header fields" attribute to true and consider "desync mitigation mode" defensive or strictest.
  • Make sure the application's HTTP keep-alive timeout is longer than the ALB idle timeout (for example ALB 60 s, nginx keepalive_timeout 75 s, Node.js server.keepAliveTimeout 65000 ms).

Common live issue: intermittent 502 errors at low rates (0.1 to 1 percent) that nobody can reproduce. Cause: Node.js default keep-alive timeout is 5 seconds; the backend closes an idle connection exactly when the ALB reuses it. Fix: set keep-alive timeout above 60 seconds on the application server.

2.4 Network Load Balancer (NLB) - Production importance: High (when used)

  • Layer 4: forwards TCP, UDP, or TLS connections without inspecting HTTP. Handles millions of requests per second with very low latency.
  • One static IP per AZ, optionally your own Elastic IPs. Useful when customers must allow-list your IPs.
  • Client IP preservation: with instance targets, the target sees the real client IP. This means the EC2 security group must allow the client IP ranges (or 0.0.0.0/0), not just the NLB. This surprises many people.
  • Proxy Protocol v2 can pass client IP information when preservation is not possible.
  • Security groups on NLB are supported but must be associated at creation time; you cannot add them later to an NLB created without one.
  • TLS listener: NLB can terminate TLS with an ACM certificate, or use a TCP listener for TLS pass-through so the backend handles certificates (needed for end-to-end mTLS by the app).
  • Cross-zone load balancing is off by default on NLB (see 2.11).
  • Health checks can be TCP, HTTP, or HTTPS.

Common live issue: NLB created, targets show healthy, but clients time out. Cause: client IP preservation is on, and web-sg only allows traffic from the VPC CIDR. Health checks pass because they come from NLB private IPs inside the VPC. Fix: allow client CIDRs on the instance security group, or attach a security group to the NLB at creation and reference it.

2.6 Target groups - Production importance: Critical

A target group is a named pool of backends plus the rules for checking them and sending traffic to them. Listeners and rules forward to target groups; Auto Scaling groups attach to target groups.

Key settings:

  • Target type: instance (EC2 instance IDs), ip (private IPs, including on-premises over VPN/Direct Connect), lambda (ALB only), alb (NLB only). Cannot be changed after creation.
  • Protocol and port: the port traffic is sent to on the target, for example HTTP 80 or HTTP 8080.
  • Health check settings (section 2.8).
  • Attributes: deregistration delay, stickiness, slow start duration, load balancing algorithm, cross-zone setting.

Slow start: newly registered targets receive a linearly increasing share of traffic over 30 to 900 seconds. Useful for apps with cold caches or JIT warmup (Java).

Weighted target groups: one forward action can split traffic between target groups by weight, for example 90/10. This is the basis for blue/green and canary deployments on ALB.

Take care in live:

  • Use one target group per service or per deployment colour. Do not share a target group between unrelated apps.
  • Name target groups clearly (env-app-port), because target group names are limited to 32 characters and appear in alarms.
  • Watch the metrics HealthyHostCount, UnHealthyHostCount, TargetResponseTime, RequestCountPerTarget, HTTPCode_Target_5XX_Count.

2.7 EC2 as a target

  • With target type instance, the load balancer sends traffic to the primary private IP of the instance's primary network interface, on the target group port (or a per-target port override).
  • The instance must be in the same VPC as the target group. Instances in peered VPCs or on-premises require target type ip.
  • The instance security group must allow the target port and health check port from the load balancer security group (ALB) or from the relevant sources (NLB).
  • Manual registration: register-targets / deregister-targets. With Auto Scaling, registration is automatic (section 6.2).
  • The same instance can be registered on multiple ports (useful for containers with dynamic port mapping).
  • Instances do not need public IPs. They should be in private subnets with outbound access via NAT Gateway or VPC endpoints for package installs and AWS APIs.
aws elbv2 register-targets --target-group-arn $TG_ARN --targets Id=i-0abc123 Id=i-0def456
aws elbv2 describe-target-health --target-group-arn $TG_ARN

Target states you will see: initial (registration in progress, health checks running), healthy, unhealthy, unused (target not in an enabled AZ, or target group not attached to a listener), draining (deregistering), unavailable (health checks disabled).

Common live issue: target stuck in "unused". Cause: the instance is in an AZ that is not enabled on the load balancer, or the target group is not used by any listener rule. Fix: add a subnet in that AZ to the load balancer, or attach the target group to a listener.

2.8 Load balancer health checks - Production importance: Critical

The load balancer periodically calls each target and decides whether it is healthy. Unhealthy targets stop receiving new requests.

Time to detect failure is about interval multiplied by unhealthy threshold. Time for a new instance to start receiving traffic is about interval multiplied by healthy threshold. With defaults, a new instance waits 150 seconds after the app is up before getting traffic.

Shallow vs deep health checks:

  • Shallow (liveness): returns 200 if the process can serve HTTP. Recommended for the load balancer health check.
  • Deep (readiness with dependencies): also checks the database, cache, and downstream APIs. Dangerous as a load balancer health check, because one dependency outage marks every instance unhealthy at the same time.

Fail open: if every target in a target group is unhealthy, ALB routes traffic to all of them anyway (because sending to possibly-broken targets is better than sending to none). Do not rely on this; it means your alarms should already be firing.

Common live issue (classic outage): the /health endpoint checks database connectivity. The database has a 30 second failover. All instances fail health checks. If the Auto Scaling group uses ELB health checks, it terminates every instance and launches new ones, which also fail, so the app stays down long after the database recovers. Fix: keep the load balancer health check shallow; report dependency status on a separate endpoint for monitoring; use circuit breakers in the app.

Other common health check issues:

  • Health check path redirects to /login (HTTP 302). Default matcher is 200, so targets are unhealthy. Fix: dedicated /health path that returns 200 without authentication.
  • App only allows certain Host headers (Django ALLOWED_HOSTS, Spring, nginx server_name). Health checks use the target's IP as the Host header and get 400. Fix: allow the private IP or exempt the health path.
  • Security group allows port 80 but the health check uses port 8081. Fix: allow the health check port from alb-sg.
  • Heavy health check endpoint (renders a full page) adds measurable load. With many load balancer nodes, each node checks each target independently, so health check traffic is higher than you expect.

2.9 Connection draining (deregistration delay) - Production importance: High

Connection draining is the Classic Load Balancer name; on ALB and NLB it is called deregistration delay. When a target is deregistered (scale in, instance refresh, manual), the load balancer stops sending it new requests but lets in-flight requests finish for up to the delay period. The target is in the draining state.

  • Default: 300 seconds. Range 0 to 3600.
  • Set it slightly longer than your longest normal request. For a typical API with requests under 10 seconds, 30 to 60 seconds is common.
  • Too long: deployments and scale-in are slow; instances you are paying for sit draining for 5 minutes each.
  • Too short: long uploads, reports, or WebSocket connections are cut, causing user-visible errors during every deployment.
  • Auto Scaling waits for deregistration to complete before terminating the instance.
  • The application should also handle SIGTERM gracefully: stop accepting new work, finish current work, then exit.
aws elbv2 modify-target-group-attributes --target-group-arn $TG_ARN \
  --attributes Key=deregistration_delay.timeout_seconds,Value=60

Common live issue: "every deployment causes a burst of 502s". Cause: deregistration delay set to 0 by someone trying to speed up deployments, or the app process is killed before draining ends. Fix: restore a sensible delay, and use a lifecycle hook on termination if the app needs extra shutdown time (section 5.1).

2.10 Sticky sessions (session affinity) - Production importance: Medium

Stickiness binds a client to the same target for a period, using a cookie.

  • Duration-based (load balancer generated cookie, named AWSALB): duration 1 second to 7 days, default 1 day.
  • Application-based: your app sets its own cookie; the ALB generates AWSALBAPP to track it. Use when the app controls session lifetime.
  • NLB stickiness is based on source IP, not cookies.
  • If the sticky target becomes unhealthy or is deregistered, the client is moved to another target (and loses any local session data).
  • Clients must support cookies. API clients and mobile apps often do not send cookies back, so stickiness silently does nothing.
aws elbv2 modify-target-group-attributes --target-group-arn $TG_ARN \
  --attributes Key=stickiness.enabled,Value=true Key=stickiness.type,Value=lb_cookie \
               Key=stickiness.lb_cookie.duration_seconds,Value=3600

Take care in live: stickiness is a workaround for stateful apps, not a design goal. It causes uneven load and reduces the benefit of scaling out, because existing users stay on old instances while new instances only get new users.

Common live issue: after scale-out under heavy load, CPU on the original instances stays at 90 percent while new instances sit at 10 percent. Cause: long stickiness duration. Fix: shorter duration, or move sessions to a shared store and disable stickiness.

2.11 Cross-zone load balancing - Production importance: High

A load balancer has a node in each enabled AZ. DNS returns IPs of all nodes, so clients spread roughly evenly across nodes.

  • Cross-zone on: each node distributes traffic across all registered targets in all AZs.
  • Cross-zone off: each node only sends to targets in its own AZ.

Example: AZ-a has 2 instances, AZ-b has 8 instances. Each AZ node gets 50 percent of traffic.

  • Off: each AZ-a instance gets 25 percent, each AZ-b instance gets 6.25 percent. AZ-a instances overload.
  • On: each instance gets 10 percent.

2.12 TLS termination - Production importance: Critical

TLS termination means the load balancer decrypts HTTPS traffic using a certificate, so instances do not need to handle certificates.

  • Certificates: use AWS Certificate Manager (ACM). Public ACM certificates are free and renew automatically if validated via DNS (CNAME record in Route 53). Imported certificates do not auto-renew.
  • HTTPS listener on 443 with a certificate and a security policy. Use a modern policy that supports TLS 1.3 and 1.2, for example ELBSecurityPolicy-TLS13-1-2-2021-06 (check the current recommended policy in the docs).
  • SNI: one HTTPS listener can serve many certificates (many domains); the ALB picks based on the host name the client requests.
  • HTTP listener on 80 should only redirect to HTTPS (HTTP 301).
  • Backend encryption options:
    • Termination only: ALB to EC2 over HTTP inside the VPC. Common and acceptable for many workloads.
    • Re-encryption: ALB to EC2 over HTTPS (target group protocol HTTPS). Required by many compliance standards. The ALB does not validate the target certificate, so a self-signed certificate on the instance works.
    • Pass-through: NLB TCP listener on 443, the instance terminates TLS. Needed when the app must see the client certificate or keys must never leave the instance.
  • Mutual TLS (client certificates): ALB supports mTLS with a trust store, in verify mode or pass-through mode.
  • The app should use the X-Forwarded-Proto header to know the original request was HTTPS (for redirects and secure cookies).
# HTTPS listener
aws elbv2 create-listener --load-balancer-arn $ALB_ARN --protocol HTTPS --port 443 \
  --certificates CertificateArn=$CERT_ARN \
  --ssl-policy ELBSecurityPolicy-TLS13-1-2-2021-06 \
  --default-actions Type=forward,TargetGroupArn=$TG_ARN

# HTTP to HTTPS redirect
aws elbv2 create-listener --load-balancer-arn $ALB_ARN --protocol HTTP --port 80 \
  --default-actions '[{"Type":"redirect","RedirectConfig":{"Protocol":"HTTPS","Port":"443","StatusCode":"HTTP_301"}}]'

Common live issues:

  • Certificate expiry outage: an imported certificate (bought from a third party) expired because nobody owned renewal. Fix: use ACM-issued certificates with DNS validation, or alarm on the ACM DaysToExpiry metric and the AWS Health / EventBridge expiry events.
  • ACM certificate stuck in "pending renewal": the DNS validation CNAME was deleted during a DNS cleanup. Fix: never delete the _acme style validation CNAME records ACM created.
  • Infinite redirect loop: the app redirects HTTP to HTTPS itself, but sees HTTP from the ALB (because of termination). Fix: the app must trust X-Forwarded-Proto.
  • Old clients fail after tightening the TLS policy (legacy Android, old Java clients, IoT devices). Fix: check the ALB access logs for TLS protocol and cipher fields before changing the policy.

Module 3 - Auto Scaling fundamentals

3.1 What is Auto Scaling?

Amazon EC2 Auto Scaling automatically maintains and adjusts the number of EC2 instances in a group. It does three jobs:

  • Fleet management: keeps the number of running, healthy instances equal to the desired capacity. If an instance dies, it is replaced. This is valuable even with a fixed size (min = max = desired).
  • Dynamic scaling: changes desired capacity based on metrics (CPU, requests, queue depth).
  • Scheduled and predictive scaling: changes capacity based on time or forecasts.

Other related services, so you do not confuse them: AWS Auto Scaling (a console for scaling plans across services), Application Auto Scaling (scales ECS services, DynamoDB, Aurora replicas, Lambda concurrency, etc.). This guide is about EC2 Auto Scaling.

Auto Scaling has no extra charge.

3.2 Launch template - Production importance: Critical

A launch template is the blueprint for instances the Auto Scaling group launches: AMI, instance type, key pair, security groups, IAM instance profile, user data, EBS volumes, network settings, metadata options, tags, and more.

  • Versioned: each change creates a new version. There is a Default version and a Latest version.
  • The ASG can reference a specific version number, $Default, or $Latest.
  • Supports features launch configurations do not: mixed instance types and purchase options (On-Demand plus Spot), multiple network interfaces, capacity reservations, placement groups, T2/T3 unlimited, dedicated hosts, IMDSv2 enforcement, and instance refresh rollback.
  • The AMI can be an SSM parameter reference (resolve:ssm:parameter-name), so the template picks up the latest AMI published to that parameter at launch time.

Example template data (lt.json):

{
  "ImageId": "resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64",
  "InstanceType": "t3.micro",
  "SecurityGroupIds": ["sg-web"],
  "IamInstanceProfile": { "Name": "web-ec2-role" },
  "MetadataOptions": { "HttpTokens": "required", "HttpEndpoint": "enabled", "HttpPutResponseHopLimit": 2 },
  "Monitoring": { "Enabled": true },
  "UserData": "BASE64_OF_USER_DATA_SCRIPT",
  "TagSpecifications": [
    { "ResourceType": "instance", "Tags": [ { "Key": "Name", "Value": "web" }, { "Key": "env", "Value": "lab" } ] },
    { "ResourceType": "volume",   "Tags": [ { "Key": "env", "Value": "lab" } ] }
  ]
}
base64 -w0 userdata.sh   # paste output into UserData
aws ec2 create-launch-template --launch-template-name web-lt \
  --version-description v1 --launch-template-data file://lt.json

# new version that changes only the instance type, based on version 1
aws ec2 create-launch-template-version --launch-template-name web-lt \
  --source-version 1 --version-description v2-t3small \
  --launch-template-data '{"InstanceType":"t3.small"}'

Take care in live:

  • Version strategy: if the ASG uses $Latest, anyone who creates a new template version changes what future scale-out events launch, without a deployment. Many teams prefer a specific version number (or $Default) and roll forward deliberately with instance refresh.
  • Enforce IMDSv2 (HttpTokens required). Set hop limit 2 if containers on the instance need metadata.
  • Do not put secrets in user data; it is readable by anyone with ec2:DescribeInstanceAttribute and from inside the instance. Fetch secrets from Secrets Manager at boot.
  • Encrypt EBS volumes (account-level default encryption is the simplest).
  • Prefer baked AMIs (built with EC2 Image Builder or Packer) over long user data scripts. Faster boot means faster scaling and less dependence on external package repositories.

Common live issue: a scale-out event during peak traffic fails with launch errors. Cause: the launch template references an AMI that was deregistered during a cleanup, or a security group that was deleted. The ASG had been running fine for months because it never needed to launch. Fix: protect AMIs used by live templates, alarm on failed launches (EventBridge event "EC2 Instance Launch Unsuccessful"), and periodically test scaling.

3.4 Auto Scaling group (ASG)

An ASG is a logical group of EC2 instances managed as a unit. Its key properties:

  • Launch template (and version) or mixed instances policy.
  • VPC subnets (one or more per AZ) - the ASG spreads instances across them.
  • Capacity: minimum, desired, maximum.
  • Health check type (EC2, ELB, and others) and health check grace period.
  • Attached load balancer target groups.
  • Scaling policies, scheduled actions, lifecycle hooks, warm pool.
  • Termination policies, instance maintenance policy, default instance warmup, capacity rebalancing for Spot.
  • Tags (optionally propagated to instances).

Mixed instances policy (Production importance: High): specify several instance types (for example m6i.large, m5.large, m6a.large, m7i.large) and an On-Demand / Spot split. This reduces the risk of "InsufficientInstanceCapacity" in one AZ and lowers cost. Attribute-based instance type selection lets you specify vCPU and memory ranges instead of naming types.

aws autoscaling create-auto-scaling-group --auto-scaling-group-name web-asg \
  --launch-template LaunchTemplateName=web-lt,Version='$Default' \
  --min-size 2 --desired-capacity 2 --max-size 6 \
  --vpc-zone-identifier "subnet-priv-a,subnet-priv-b" \
  --target-group-arns $TG_ARN \
  --health-check-type ELB --health-check-grace-period 120 \
  --default-instance-warmup 120 \
  --tags Key=env,Value=lab,PropagateAtLaunch=true

3.5 Minimum, desired, and maximum capacity - Production importance: Critical

  • Minimum capacity: the group never goes below this. It is your guaranteed baseline for availability. Scaling policies cannot scale in below it.
  • Desired capacity: the number the ASG is trying to run right now. Scaling policies and scheduled actions change this number. If actual differs from desired, the ASG launches or terminates to match.
  • Maximum capacity: the group never goes above this (except briefly during AZ rebalancing or instance refresh with max healthy percentage above 100). It is your cost and blast-radius ceiling.
  • Rule: min less than or equal to desired, desired less than or equal to max.

How to choose values in production:

  • Minimum: enough to serve normal traffic if one AZ is lost. With 2 AZs, minimum should be at least 2 (one per AZ). For critical services, size minimum so that the remaining AZs can carry normal load while the ASG backfills: for example, if normal load needs 4 instances and you use 2 AZs, losing one AZ leaves half the fleet, so a conservative minimum is 8 (4 per AZ). With 3 AZs the same goal needs only 6 (2 per AZ), which is one reason 3 AZs are cheaper for high availability.
  • Maximum: high enough for the worst realistic spike, low enough to cap runaway cost (for example, a bug causing CPU loops would otherwise scale you to hundreds of instances). Check that the account EC2 vCPU service quota allows the maximum.
  • Desired: if you manage the ASG with Terraform or CloudFormation, avoid hard-coding desired capacity, or configure the tool to ignore changes to it. Otherwise every infrastructure deploy resets desired capacity to the template value, possibly scaling in a fleet that is handling peak traffic.

Common live issue: during a traffic spike, the ASG stays at 10 instances while CPU is at 95 percent. Cause: max capacity was 10, set years ago. The scaling activity history shows "at maximum capacity". Fix: alarm when GroupDesiredCapacity equals GroupMaxSize, and review max capacity quarterly.

Common live issue: a Terraform apply during business hours set desired capacity from 14 back to 2. Cause: desired_capacity hard-coded. Fix: lifecycle ignore_changes on desired_capacity, or omit it.

3.6 Multi-AZ Auto Scaling - Production importance: Critical

  • Give the ASG subnets in at least 2, preferably 3, AZs. The ASG tries to keep the number of instances balanced across AZs.
  • AZ rebalancing: if the group becomes unbalanced (an AZ had no capacity, or you manually terminated instances), the ASG launches new instances in the under-populated AZ first and then terminates in the over-populated AZ. During this it can temporarily exceed max capacity by up to 10 percent (or 1 instance).
  • If an AZ fails, the ASG launches replacement instances in the remaining AZs.
  • The load balancer must have subnets in the same AZs as the ASG, otherwise targets are "unused".
  • Capacity rebalancing (Spot): proactively replaces Spot instances that receive a rebalance recommendation.
  • For EC2 in private subnets, deploy one NAT Gateway per AZ. A single NAT Gateway in one AZ means an AZ failure breaks outbound access for every instance.

Common live issue: one AZ runs out of the requested instance type (InsufficientInstanceCapacity). The ASG keeps trying, launching extra instances in other AZs, leaving the fleet unbalanced. Fix: use a mixed instances policy with 3 or more similar instance types, and use 3 AZs.

Common live issue: AZ rebalancing terminates instances in the middle of long jobs. Fix: use scale-in protection on busy instances, or suspend the AZRebalance process for workloads that cannot tolerate it (and understand the trade-off).

3.7 Auto Scaling health checks - Production importance: Critical

The ASG decides whether each instance is healthy, separate from the load balancer's view. Health check sources:

  • EC2 (always on): instance state must be running, and EC2 system and instance status checks must pass. Detects hardware failure, kernel panic, stopped instances. Does not detect a crashed application.
  • ELB (opt-in): if the target group reports the instance unhealthy, the ASG marks it unhealthy. Detects application failures. Recommended for instances behind a load balancer.
  • EBS (opt-in): detects impaired EBS volumes.
  • VPC Lattice (opt-in): when using VPC Lattice target groups.
  • Custom: your monitoring calls set-instance-health to mark an instance unhealthy.

Health check grace period: after an instance enters the InService state, the ASG waits this long before acting on failed health checks. The console default is 300 seconds; when created through the CLI or API the default is 0. Set it to the time your instance needs from launch to passing health checks, with some margin.

aws autoscaling update-auto-scaling-group --auto-scaling-group-name web-asg \
  --health-check-type ELB --health-check-grace-period 180

# custom health signal from your monitoring
aws autoscaling set-instance-health --instance-id i-0abc123 --health-status Unhealthy

Common live issue (replacement loop): instances are launched, then terminated after 2 to 3 minutes, over and over. The ASG activity history shows "an instance was taken out of service in response to an ELB system health check failure". Cause: the application takes 6 minutes to start (large Java app, big user data script), but the grace period is 120 seconds. Fix: increase the grace period, speed up boot by baking the AMI, or use a launch lifecycle hook so the instance only goes InService when ready.

Common live issue: the ASG uses only EC2 health checks. The application process crashed on one instance; the load balancer stopped routing to it, but the ASG keeps it running forever because the EC2 status checks pass. Capacity is silently reduced. Fix: enable ELB health checks on the ASG.

3.8 Replacement of unhealthy instances

  • Once an instance is marked unhealthy, the ASG schedules it for replacement. It terminates the unhealthy instance and launches a new one to restore desired capacity.
  • The instance maintenance policy controls order and capacity during replacement: minimum healthy percentage (for example 100 means launch the replacement before terminating), and maximum healthy percentage (for example 110 allows extra capacity during replacement). Without a policy, the default is terminate then launch.
  • Unhealthy instances are not repaired or rebooted. They are replaced. That is why instances must be disposable.
  • Scale-in protection does not protect an instance from health replacement.
  • Termination lifecycle hooks still run, which lets you collect logs from the failing instance before it disappears.
  • The ReplaceUnhealthy and HealthCheck processes can be suspended, which stops this behaviour. Useful for debugging, dangerous if forgotten.
aws autoscaling update-auto-scaling-group --auto-scaling-group-name web-asg \
  --instance-maintenance-policy MinHealthyPercentage=100,MaxHealthyPercentage=110

Common live issue: an engineer suspends ReplaceUnhealthy to debug a broken instance, then forgets. Weeks later, instances fail and are never replaced. Fix: alarm or AWS Config rule on suspended processes; use a ticket or calendar reminder whenever suspending.

Common live issue: logs from crashed instances are gone, so the root cause is unknown. Fix: ship logs continuously to CloudWatch Logs; add a termination lifecycle hook that uploads diagnostic data to S3.

4.2 Scaling based on CloudWatch - Production importance: High

Every dynamic scaling policy is driven by CloudWatch metrics and alarms.

  • EC2 metrics: CPUUtilization, NetworkIn/Out, etc. Basic monitoring sends 5-minute data (free). Detailed monitoring sends 1-minute data (paid) and is recommended for scaling so policies react faster.
  • Memory and disk usage are not provided by default. Install the CloudWatch agent to publish them.
  • ALB metrics: RequestCountPerTarget, TargetResponseTime, HTTPCode_Target_5XX_Count.
  • ASG group metrics: GroupMinSize, GroupMaxSize, GroupDesiredCapacity, GroupInServiceInstances, GroupPendingInstances, GroupTerminatingInstances, GroupTotalInstances, warm pool metrics. They must be enabled on the ASG (free, 1-minute granularity). Enable them; you need them in dashboards.
  • Custom metrics: anything your app publishes, for example active connections, jobs in progress, or queue backlog per instance.
  • Metric math: target tracking can use metric math, for example SQS ApproximateNumberOfMessagesVisible divided by GroupInServiceInstances, which gives "backlog per instance". This is the recommended way to scale queue workers.
aws autoscaling enable-metrics-collection --auto-scaling-group-name web-asg --granularity "1Minute"

Choosing the right metric:

  • The metric must increase when you need more instances and decrease when you add instances. CPU and request count per target do. Total request count for the whole ALB does not decrease when you add instances, so it is a bad target tracking metric.
  • Latency (TargetResponseTime) is a poor scaling metric on its own because it can rise for reasons more instances do not fix (slow database).
  • For CPU-bound apps use CPU. For IO-bound web apps, request count per target is often better. For workers, backlog per instance.

Common live issue: scaling policy never triggers. The alarm is in INSUFFICIENT_DATA state. Cause: custom metric dimension mismatch (the app publishes with dimension InstanceId, but the alarm uses AutoScalingGroupName), or the metric stopped publishing after an agent configuration change. Fix: verify the exact namespace, metric name, and dimensions; alarm on INSUFFICIENT_DATA for scaling alarms.

4.3 Target tracking scaling - Production importance: Critical

You choose a metric and a target value, for example average CPU at 50 percent. Auto Scaling creates and manages CloudWatch alarms and calculates how many instances are needed to bring the metric back to the target.

  • Predefined metrics: ASGAverageCPUUtilization, ASGAverageNetworkIn, ASGAverageNetworkOut, ALBRequestCountPerTarget. Custom metrics and metric math are also supported.
  • Scale out reacts quickly (alarm on about 3 minutes of breaching data with 1-minute metrics). Scale in is deliberately slower and more conservative (about 15 minutes), to avoid flapping.
  • The alarms are named TargetTracking-...; do not edit or delete them manually. Auto Scaling owns them.
  • Option to disable scale-in: the policy only adds capacity; you remove capacity by schedule or another policy.
  • With multiple target tracking policies, the ASG scales out if any policy wants more, and scales in only if all policies agree.
  • Target values: 50 to 70 percent CPU is typical. Lower targets mean more headroom for sudden spikes and slower scale-out, at a higher cost.
# CPU target tracking
aws autoscaling put-scaling-policy --auto-scaling-group-name web-asg \
  --policy-name cpu-50 --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{
    "PredefinedMetricSpecification": { "PredefinedMetricType": "ASGAverageCPUUtilization" },
    "TargetValue": 50.0
  }'

# Request count per target (ResourceLabel = app/ALB-name/ALB-id/targetgroup/TG-name/TG-id)
aws autoscaling put-scaling-policy --auto-scaling-group-name web-asg \
  --policy-name req-per-target-500 --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{
    "PredefinedMetricSpecification": {
      "PredefinedMetricType": "ALBRequestCountPerTarget",
      "ResourceLabel": "app/web-alb/1234567890abcdef/targetgroup/web-tg/abcdef1234567890"
    },
    "TargetValue": 500.0
  }'

How to find the right request count target: load test a single instance and find the requests per minute at which latency starts degrading. Set the target to about 60 to 70 percent of that number.

Common live issue: flapping (instances repeatedly added and removed). Cause: target value too close to the natural fluctuation, very short instance warmup, or a metric that drops sharply when instances are added. Fix: set default instance warmup properly, raise or lower the target, or use a less noisy metric.

4.4 Step scaling

You create a CloudWatch alarm yourself and attach a step scaling policy. The policy defines steps based on how far above or below the alarm threshold the metric is.

Example: alarm threshold CPU 60 percent.

  • 60 to 80 percent (0 to 20 above threshold): add 1 instance.
  • Above 80 percent (20 or more above threshold): add 3 instances.
  • Adjustment types: ChangeInCapacity (add or remove N), ExactCapacity (set to N), PercentChangeInCapacity (add or remove N percent, with MinAdjustmentMagnitude).
  • Step bounds are relative to the alarm threshold, not absolute values. This is the most common source of confusion.
  • Step scaling does not use cooldown; it uses instance warmup. It can continue to respond to new alarm breaches while instances are warming up, but it accounts for warming instances so it does not over-add.
  • You need separate policies and alarms for scale-out and scale-in.
POLICY_ARN=$(aws autoscaling put-scaling-policy --auto-scaling-group-name web-asg \
  --policy-name cpu-step-out --policy-type StepScaling \
  --adjustment-type ChangeInCapacity --metric-aggregation-type Average \
  --step-adjustments MetricIntervalLowerBound=0,MetricIntervalUpperBound=20,ScalingAdjustment=1 \
                     MetricIntervalLowerBound=20,ScalingAdjustment=3 \
  --query 'PolicyARN' --output text)

aws cloudwatch put-metric-alarm --alarm-name web-asg-cpu-high \
  --namespace AWS/EC2 --metric-name CPUUtilization --statistic Average \
  --dimensions Name=AutoScalingGroupName,Value=web-asg \
  --period 60 --evaluation-periods 2 --threshold 60 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions $POLICY_ARN

When to prefer step over target tracking: when you want a specific, explainable reaction (for example "at 90 percent, add 5 immediately"), when scaling on a metric that does not change proportionally with capacity, or when you need asymmetric behaviour.

4.5 Simple scaling

  • One alarm, one adjustment (for example add 1 instance). After the action, the ASG waits for the cooldown period (default 300 seconds) before responding to further alarms of simple policies.
  • Problem: during a fast spike, it adds 1 instance and then waits 5 minutes, adding 1 more, and so on. Too slow.
  • Still exists for backward compatibility. Know it for exams and older environments; use step or target tracking in new designs.

Common live issue: an old environment uses simple scaling with +1 instance and 300 second cooldown. A marketing campaign multiplies traffic by 5; it takes 40 minutes to reach required capacity, with errors throughout. Fix: replace with target tracking, and use scheduled scaling for known events.

4.6 Scheduled scaling - Production importance: High

  • A scheduled action sets min, max, and/or desired capacity at a specific time, once or on a recurring cron schedule.
  • Supports a time zone (for example Asia/Kolkata), including daylight saving handling for zones that use it.
  • Dynamic policies continue to work within the new min and max.
  • Use cases: scale up before business hours, scale down at night and weekends (dev and test environments can go to 0), pre-scale for a sale or a known event.
# weekday morning scale up (IST)
aws autoscaling put-scheduled-update-group-action --auto-scaling-group-name web-asg \
  --scheduled-action-name weekday-morning-up --recurrence "30 8 * * 1-5" --time-zone "Asia/Kolkata" \
  --min-size 4 --max-size 12 --desired-capacity 4

# evening scale down
aws autoscaling put-scheduled-update-group-action --auto-scaling-group-name web-asg \
  --scheduled-action-name weekday-evening-down --recurrence "0 21 * * 1-5" --time-zone "Asia/Kolkata" \
  --min-size 2 --max-size 6

# one-time event
aws autoscaling put-scheduled-update-group-action --auto-scaling-group-name web-asg \
  --scheduled-action-name diwali-sale --start-time "2026-11-05T06:00:00Z" \
  --min-size 10 --max-size 40 --desired-capacity 10

Take care in live:

  • Scale up early enough to account for boot time and health checks (for example 30 minutes before the event, not at the exact minute).
  • Raise the minimum, not just desired. If you only set desired, target tracking may scale in again before the traffic arrives.
  • Always pair a scale-up action with a scale-down action, or remember to remove a one-time raised minimum.
  • Cron uses the time zone you specify; without it, UTC is used. Wrong time zone is a classic mistake.

Common live issue: the evening scale-down action sets min to 1 but a team later raised production min to 3 manually for resilience. Every evening the schedule silently lowers min back to 1. Fix: keep all capacity settings in infrastructure as code, review scheduled actions whenever min/max is changed.

4.7 Predictive scaling

  • Analyses historical load (needs at least 24 hours; uses up to 14 days) and forecasts capacity for the next 48 hours, refreshed regularly.
  • Launches instances ahead of the forecast demand, so capacity is ready before the daily peak. Ideal for slow-booting apps with regular cycles.
  • Modes: forecast only (generate forecasts so you can evaluate accuracy in the console, no scaling) and forecast and scale.
  • Metrics: CPU, network, ALB request count per target, or custom metric pairs (load metric and scaling metric).
  • Scheduling buffer time: how many seconds before the forecast time instances should launch (for example 300 to 600 seconds for apps that take a few minutes to become ready).
  • Max capacity behaviour: can optionally allow the forecast to raise capacity above max by a buffer.
  • Predictive scaling only scales out ahead of time; it does not handle unexpected spikes. Always combine it with target tracking.
aws autoscaling put-scaling-policy --auto-scaling-group-name web-asg \
  --policy-name cpu-predictive --policy-type PredictiveScaling \
  --predictive-scaling-configuration '{
    "MetricSpecifications": [ {
      "TargetValue": 50,
      "PredefinedMetricPairSpecification": { "PredefinedMetricType": "ASGCPUUtilization" }
    } ],
    "Mode": "ForecastOnly",
    "SchedulingBufferTime": 300
  }'

Take care in live: start in forecast-only mode for at least a week, compare forecast vs actual in the console, then switch to forecast and scale. Do not use it for irregular, event-driven, or newly launched workloads with no history.

Common live issue: after a one-time event (huge sale day), predictive scaling repeats extra capacity at the same hour on following days because the event is in the history. Fix: review forecasts after unusual events; temporarily switch to forecast only.

4.8 Cooldown, warmup, and combining policies - Production importance: High

  • Default cooldown (default 300 s): only applies to simple scaling policies. After a simple scaling activity, other simple policies wait.
  • Default instance warmup (recommended to enable on every ASG): the time after an instance is InService before its metrics count toward the group's metrics, and before it is considered as contributing capacity. Used by target tracking, step scaling, and instance refresh. Set it to how long the instance takes to reach steady-state performance (often 60 to 300 seconds).
  • Why warmup matters: a booting instance shows high CPU (installing packages, JIT compiling) or zero requests. Without warmup, these numbers distort the average and cause extra scaling.
  • Multiple policies: if several policies trigger at the same time, the ASG chooses the one that results in the largest capacity, for both scale-out and scale-in. This favours availability.
  • Scheduled actions change min/max/desired; dynamic policies then operate within those limits.

Common live issue: CPU-based scaling adds 2 instances, then 2 more a minute later, then 2 more, overshooting to max. Cause: new instances run a heavy user data script at 100 percent CPU, which pushes the group average up. No instance warmup configured. Fix: set default instance warmup to boot time plus margin; bake AMIs to reduce boot work.

Module 5 - Advanced Auto Scaling operations

5.1 Lifecycle hooks - Production importance: High

A lifecycle hook pauses an instance during launch or termination so you can run custom actions before it continues.

Launch:      Pending --> Pending:Wait --(your action)--> Pending:Proceed --> InService
Termination: Terminating --> Terminating:Wait --(your action)--> Terminating:Proceed --> Terminated
  • Transitions: autoscaling:EC2_INSTANCE_LAUNCHING and autoscaling:EC2_INSTANCE_TERMINATING.
  • Heartbeat timeout: how long the instance waits (30 to 7200 seconds, default 3600). Extend with record-lifecycle-action-heartbeat. Overall maximum is 48 hours or 100 heartbeats, whichever is smaller.
  • Default result when the timeout expires: CONTINUE or ABANDON. For launch hooks, ABANDON terminates the instance. For termination hooks, both results continue termination.
  • Complete the action early with complete-lifecycle-action (from the instance itself, a Lambda, or any automation).
  • Notifications: EventBridge (recommended, triggers Lambda or SSM Automation), SNS, or SQS. The instance can also poll its own lifecycle state from instance metadata (autoscaling/target-lifecycle-state).
  • Hooks also apply when instances move in and out of a warm pool.

Typical uses:

  • Launch: wait until the app has fully started, warmed caches, downloaded models, joined a cluster, or registered in a service discovery system, then complete the action. The instance is registered with the target group only after it goes InService.
  • Termination: upload logs to S3, finish in-progress jobs, deregister from a non-ELB system (Consul, license server, Active Directory), take a final snapshot.
aws autoscaling put-lifecycle-hook --auto-scaling-group-name web-asg \
  --lifecycle-hook-name launch-ready --lifecycle-transition autoscaling:EC2_INSTANCE_LAUNCHING \
  --heartbeat-timeout 600 --default-result ABANDON

aws autoscaling put-lifecycle-hook --auto-scaling-group-name web-asg \
  --lifecycle-hook-name drain-logs --lifecycle-transition autoscaling:EC2_INSTANCE_TERMINATING \
  --heartbeat-timeout 300 --default-result CONTINUE

# at the end of user data, once the app is verified healthy:
aws autoscaling complete-lifecycle-action --auto-scaling-group-name web-asg \
  --lifecycle-hook-name launch-ready --instance-id $ID --lifecycle-action-result CONTINUE --region ap-south-1

The instance role needs autoscaling:CompleteLifecycleAction for the instance to complete its own hook.

Take care in live:

  • Use default result ABANDON for launch hooks, so a broken instance that never signals readiness is terminated rather than added to service.
  • Keep the heartbeat timeout realistic. Long timeouts slow every scaling event.
  • Lifecycle hook time counts against scaling speed: a 10-minute launch hook means 10 minutes before new capacity serves traffic.

Common live issue: scale-out takes an hour. Instances sit in Pending:Wait. Cause: the launch hook's completion call fails silently (missing IAM permission, wrong region in the CLI call, script error before the final line), and the default result is CONTINUE after a 3600 second timeout. Fix: check permissions, log the user data script output (/var/log/cloud-init-output.log), set a sensible heartbeat timeout, and use ABANDON.

5.2 Instance refresh - Production importance: Critical (for deployments)

Instance refresh replaces instances in the ASG in a rolling fashion, typically to roll out a new launch template version (new AMI, new instance type, new user data).

  • Minimum healthy percentage (default 90): how much of desired capacity must stay healthy during the refresh. 90 percent with 10 instances means 1 at a time.
  • Maximum healthy percentage (100 to 200): allows launching new instances before terminating old ones. For example min 100, max 110 means always launch first, never reduce capacity. Ideal for production.
  • Instance warmup: wait after a new instance is healthy before counting it and moving on.
  • Checkpoints: pause at given percentages (for example 20 percent and 50 percent) for a set time, to validate before continuing. A built-in canary.
  • Skip matching: do not replace instances that already match the desired configuration.
  • Desired configuration: specify the target launch template version as part of the refresh, so the ASG is updated only if the refresh succeeds.
  • Auto rollback: if the refresh fails or is cancelled, roll back to the previous configuration. Can be triggered by CloudWatch alarms (for example 5xx rate) during the refresh.
  • Instances with scale-in protection or in standby are handled according to preferences (skip, wait, or ignore).
aws autoscaling start-instance-refresh --auto-scaling-group-name web-asg \
  --desired-configuration '{"LaunchTemplate":{"LaunchTemplateName":"web-lt","Version":"2"}}' \
  --preferences '{
    "MinHealthyPercentage": 100,
    "MaxHealthyPercentage": 150,
    "InstanceWarmup": 120,
    "SkipMatching": true,
    "AutoRollback": true,
    "CheckpointPercentages": [50, 100],
    "CheckpointDelay": 300,
    "AlarmSpecification": { "Alarms": ["web-alb-5xx-high"] }
  }'

aws autoscaling describe-instance-refreshes --auto-scaling-group-name web-asg
aws autoscaling cancel-instance-refresh --auto-scaling-group-name web-asg
aws autoscaling rollback-instance-refresh --auto-scaling-group-name web-asg

Instance refresh vs other deployment methods:

  • Instance refresh: replaces whole instances (immutable infrastructure). Simple, built in.
  • Blue/green with two ASGs and weighted target groups or CodeDeploy: fastest rollback, more complex and more cost during deployment.
  • In-place deployment (CodeDeploy agent or SSM updating code on running instances): faster but creates drift; new instances launched by scaling must still get the latest code.

Common live issue: instance refresh stuck at 0 percent for hours. Cause: the new launch template version has a bug, new instances never pass health checks, and the refresh keeps waiting. Or minimum healthy percentage is 100 with maximum healthy percentage 100, so the ASG is not allowed to terminate or add anything. Fix: use alarms and auto rollback, set max healthy above 100, and test the new version in staging.

Common live issue: the refresh completed, but some instances still run old code. Cause: the ASG still points to the old version while a refresh used a different one, or skip matching was on while the change was only in an SSM parameter value (the template itself did not change). Fix: always use desired configuration with an explicit version.

5.3 Warm pools - Production importance: Medium (High for slow-boot apps)

A warm pool is a set of pre-initialized instances kept alongside the ASG. When the ASG scales out, it takes an instance from the warm pool instead of launching from scratch, which cuts scale-out time from minutes to seconds.

  • Pool states: Stopped (cheapest: pay only for EBS and Elastic IPs), Hibernated (memory saved to EBS, faster resume, requires hibernation support), Running (fastest, pay full price).
  • Size: by default the warm pool size is max capacity minus desired capacity. You can set max group prepared capacity and a minimum pool size.
  • Reuse on scale in: instead of terminating instances on scale-in, return them to the warm pool.
  • Lifecycle hooks run when instances enter and leave the pool; the instance can read its target lifecycle state from instance metadata to know whether it is going to Warmed:Stopped or InService.
  • Limitations: not supported with mixed instances policies or Spot instances, and not for instances with instance store root volumes.
aws autoscaling put-warm-pool --auto-scaling-group-name web-asg \
  --pool-state Stopped --min-size 2 --instance-reuse-policy '{"ReuseOnScaleIn": true}'
aws autoscaling describe-warm-pool --auto-scaling-group-name web-asg

Take care in live:

  • The application must handle stop and start: services set to start on boot, no assumptions that boot equals first boot, refresh configuration and credentials on start, cluster membership rejoin.
  • Instances in a warm pool keep the launch template version they were launched with. After changing the template, use instance refresh, which also refreshes warm pool instances.
  • Stopped instances still pay for EBS. A large pool of instances with big volumes adds up.

Common live issue: instances from the warm pool join the target group but serve errors. Cause: user data ran only at first launch while the instance went to the pool; on resume, the app started with stale configuration or an expired token, or the app was not enabled to start on boot. Fix: separate "initialize" from "start" logic; make the service start on boot; check target lifecycle state in scripts.

5.4 Other operational controls

  • Scale-in protection: mark instances (or set as default for new instances) so they are not chosen during scale-in. Workers can protect themselves while processing a job and remove protection when idle. Does not protect against health replacement or manual termination.
  • Standby: move an instance to Standby for troubleshooting or patching. It is deregistered from the load balancer and not health-checked, but remains in the group. Optionally decrement desired capacity so no replacement is launched. Exit standby to return it.
  • Suspend and resume processes: Launch, Terminate, AddToLoadBalancer, AlarmNotification, AZRebalance, HealthCheck, InstanceRefresh, ReplaceUnhealthy, ScheduledActions. Suspend AlarmNotification to freeze dynamic scaling during an incident investigation; always resume afterwards.
  • Termination policies (which instance to remove on scale-in): default picks the AZ with the most instances, then considers allocation strategy, then instances with the oldest launch template or configuration, then the instance closest to the next billing hour. Others: OldestInstance, NewestInstance, OldestLaunchTemplate, ClosestToNextInstanceHour, AllocationStrategy, or a custom Lambda.
  • Instance maximum lifetime: automatically replace instances older than N days (minimum 1 day). Good for enforcing regular patching and limiting drift.
  • Notifications: EventBridge events for launch and terminate success and failure. Route failures to your alerting.
aws autoscaling set-instance-protection --auto-scaling-group-name web-asg --instance-ids i-0abc123 --protected-from-scale-in
aws autoscaling enter-standby --auto-scaling-group-name web-asg --instance-ids i-0abc123 --should-decrement-desired-capacity
aws autoscaling exit-standby --auto-scaling-group-name web-asg --instance-ids i-0abc123
aws autoscaling suspend-processes --auto-scaling-group-name web-asg --scaling-processes AlarmNotification
aws autoscaling resume-processes --auto-scaling-group-name web-asg --scaling-processes AlarmNotification

Module 6 - Putting it together: Auto Scaling + ALB

6.1 Auto Scaling with ALB - Production importance: Critical

This topic appears in both of your lists (Auto Scaling with ALB, and Auto Scaling + ALB). They are the same integration, covered here.

How the two services cooperate:

  • The ASG is attached to one or more target groups (not to the load balancer directly for ALB/NLB).
  • Every instance the ASG launches is registered to all attached target groups when it becomes InService. Every instance the ASG terminates is deregistered first, with deregistration delay respected.
  • With ELB health checks enabled on the ASG, the target group's health view drives instance replacement.
  • The ALB provides the metric RequestCountPerTarget, which the ASG can use for target tracking.
  • One ASG can be attached to several target groups (for example port 80 for the web app and port 9100 for metrics), and one target group can be used by several listener rules.
aws autoscaling attach-traffic-sources --auto-scaling-group-name web-asg \
  --traffic-sources Identifier=$TG_ARN
# older equivalent:
aws autoscaling attach-load-balancer-target-groups --auto-scaling-group-name web-asg --target-group-arns $TG_ARN

Timing settings must be consistent with each other. A common, working set for a web app that boots in about 90 seconds:

6.2 Dynamic registration

  • Dynamic registration means targets are added to and removed from target groups automatically as they appear and disappear, with no manual register-targets calls.
  • For EC2: done by the ASG through the attached target groups (AddToLoadBalancer process). If you suspend AddToLoadBalancer, new instances launch but do not receive traffic; when resumed, they are not automatically registered retroactively in all cases, so check.
  • For containers on ECS: the ECS service registers each task with its dynamic host port (dynamic port mapping with bridge networking) or its own IP (awsvpc networking with target type ip). Multiple tasks can run on one instance on different ports, all in one target group.
  • For EKS: the AWS Load Balancer Controller registers pods or nodes.
  • For on-premises or other IPs: your own automation (Lambda) calls register-targets with target type ip.
  • Never manually register instances into a target group that is also managed by an ASG. Manually added instances are not managed by the ASG and are forgotten in scale-in and refresh events.

Common live issue: instances launched by the ASG are running and healthy in EC2, but receive no traffic. Causes, in order of likelihood: the ASG is not attached to the target group the listener uses (attached to an old target group from a previous deployment); AddToLoadBalancer is suspended; the instance's AZ is not enabled on the load balancer; the security group blocks the ALB. Fix: compare the ASG's attached target group ARN with the listener rule's target group ARN first.

Design principles in this architecture:

  • Security group chaining: each tier accepts traffic only from the security group of the tier in front of it. No instance is directly reachable from the internet.
  • No SSH: Session Manager for access, no port 22, no bastion host required.
  • Three AZs: losing one AZ leaves two thirds of capacity; the ASG backfills in the remaining AZs.
  • Stateless instances: sessions in ElastiCache, files in S3, data in RDS.
  • Immutable deployments: new AMI or launch template version, rolled out with instance refresh.
  • VPC endpoints reduce NAT cost and keep AWS API traffic private.

6.4 End-to-end walkthrough

Request path:

  1. The client resolves app.example.com. Route 53 returns IPs of ALB nodes in each AZ.
  2. The client connects to an ALB node over TLS. WAF inspects the request. The ALB terminates TLS using the ACM certificate.
  3. The listener rules match the request and pick target group web-tg.
  4. The ALB picks a healthy target (round robin or least outstanding requests, honouring stickiness if enabled), adds X-Forwarded-For and X-Forwarded-Proto headers, and sends the request to the instance on port 80.
  5. The instance processes the request, reads the session from ElastiCache, queries RDS, and responds.

Scale-out path:

  1. Traffic increases. RequestCountPerTarget rises above the target value.
  2. The target tracking alarm fires. The ASG increases desired capacity (for example 3 to 5).
  3. The ASG launches 2 instances from the launch template, balanced across AZs (from the warm pool if one exists).
  4. Launch lifecycle hook: the instance boots, the app starts and warms up, then signals completion.
  5. The instance goes InService and is registered to web-tg. It is in the initial state until it passes the healthy threshold.
  6. The ALB starts sending traffic (gradually, if slow start is on). After the instance warmup period, its metrics count toward the group average.

Scale-in path:

  1. Traffic falls. After the sustained period, the scale-in alarm fires and desired capacity decreases.
  2. The termination policy picks an instance (not scale-in protected), from the AZ with the most instances.
  3. The instance is deregistered from web-tg and enters draining. In-flight requests finish within the deregistration delay.
  4. Termination lifecycle hook: logs are uploaded, then the action is completed.
  5. The instance is terminated.

7.2 Production checklist

Load balancer:

  • Subnets in 2 or more AZs (3 preferred); internal vs internet-facing chosen correctly.
  • HTTPS listener with ACM certificate (DNS validated), modern TLS policy; HTTP redirects to HTTPS.
  • WAF attached (internet-facing). Deletion protection on. Access logs on. Drop invalid headers on.
  • Idle timeout reviewed; app keep-alive longer than it.
  • Route 53 alias record, not CNAME to hard-coded IPs.

Target group:

  • Dedicated shallow /health endpoint, no auth, no redirects, accepts IP Host header.
  • Interval, thresholds, and timeout tuned; health check port allowed in security group.
  • Deregistration delay matches request duration; app handles SIGTERM.
  • Stickiness only if required, with short duration.
  • Algorithm chosen (least outstanding requests for uneven request costs).

Launch template:

  • Golden AMI built by a pipeline, patched regularly; AMI protected from deletion while in use.
  • IMDSv2 required; IAM role with least privilege; no secrets in user data; EBS encrypted.
  • Detailed monitoring on; CloudWatch agent for memory, disk, and logs.
  • Tags for cost allocation propagate to instances and volumes.

Auto Scaling group:

  • Subnets in the same AZs as the load balancer, private subnets.
  • Health check type ELB; grace period above real boot time.
  • Min supports AZ loss; max covers peak and fits service quotas; desired not overwritten by IaC.
  • Default instance warmup set. Group metrics enabled.
  • Target tracking policy, plus scheduled or predictive if traffic is cyclic.
  • Mixed instance types (where possible). Instance maintenance policy with min healthy 100 for critical apps.
  • Lifecycle hooks: launch readiness (ABANDON default), termination cleanup.
  • Deployment through instance refresh with checkpoints, alarms, and auto rollback.
  • Notifications for failed launches and terminations. No processes left suspended.

Alarms (minimum set):

  • ALB: HTTPCode_ELB_5XX_Count, HTTPCode_Target_5XX_Count (as a percentage of RequestCount using metric math), TargetResponseTime p95/p99, RejectedConnectionCount.
  • Target group: UnHealthyHostCount above 0 for a sustained period, HealthyHostCount below minimum.
  • ASG: GroupDesiredCapacity equals GroupMaxSize; GroupInServiceInstances below GroupDesiredCapacity for more than 15 minutes (launches failing).
  • ACM DaysToExpiry below 30 (important for imported certificates).
  • EC2 vCPU service quota usage above 80 percent.

7.4 General things to take care of in live environments

  • Change management: test every launch template, health check, and scaling change in staging under load first. Load-test new instance types before production.
  • Infrastructure as code for everything. Manual console changes drift and get overwritten.
  • Never debug by SSH-editing a production instance that the ASG might replace; your fix disappears at the next scale event. Fix the AMI or template.
  • Test scaling regularly (monthly game day). Configuration that only runs during a rare scale-out event tends to be broken exactly then.
  • Know your boot time end to end (launch, boot, user data, app start, health check pass). It drives grace period, warmup, scheduled lead time, and whether you need warm pools.
  • Watch dependencies: scaling the web tier from 4 to 40 instances multiplies database connections by 10. Use connection pooling (RDS Proxy) and set connection limits.
  • Service quotas: EC2 vCPU limits per instance family and purchase option, ALB per region, target groups, rules per listener. Request increases before you need them.
  • Spot: if using Spot in the mix, keep a base of On-Demand, use capacity-optimized allocation, enable capacity rebalancing, and handle the 2-minute interruption notice.
  • Logging and evidence: central logs, ALB access logs, ASG activity history (kept for 6 weeks), CloudTrail for who changed what.
  • Security: no public instances, IMDSv2, least-privilege instance roles, WAF, regular AMI patching (instance maximum lifetime helps enforce).

A.5 Scenario answer key

  1. Reactive scaling cannot help when boot (5 minutes) is longer than the spike. Add a scheduled action raising min at about 8:40, or predictive scaling with a scheduling buffer of about 600 seconds, or a warm pool. Also consider a lower CPU target and faster boot via a baked AMI.
  2. The health check endpoint checked the database. During failover all targets failed, the ASG (ELB health checks) replaced every instance, and new instances also failed until the database was back, plus their boot time. Use a shallow health check; monitor dependencies separately; possibly use an instance maintenance policy and circuit breakers.
  3. The app redirects to HTTPS because it sees HTTP from the ALB (TLS terminated at the ALB). Make the app trust X-Forwarded-Proto, or let the ALB handle the redirect only.
  4. A bug (infinite loop, retry storm) caused high CPU; target tracking kept scaling to the maximum. Controls: a reasonable max, an alarm when desired equals max, budget alerts, and alarms on CPU or latency anomalies relative to request count.
  5. Deregistration delay versus upload duration (should be at least 120 to 150 seconds for this target group, or move uploads to direct-to-S3 presigned URLs), and whether the app handles SIGTERM gracefully. Check ALB access logs for 502/460 during the deployment window.
  6. Backlog per instance: SQS ApproximateNumberOfMessagesVisible divided by in-service instances, with a target based on acceptable processing latency and per-instance throughput.
  7. Cross-zone is off by default on NLB, so each AZ node gets about 50 percent of traffic and splits it only across local instances: AZ-b instances each get 25 percent while AZ-a instances get 12.5 percent. Fix by enabling cross-zone load balancing, or by balancing instance counts across AZs.
  8. Use a mixed instances policy with several equivalent instance types (or attribute-based selection) and spread across 3 AZs; consider capacity reservations for critical baseline capacity.
