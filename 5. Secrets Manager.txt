Secrets:
    - If our application running on ec2 require some secrets value,
    - we can either include them in application code statically or fetch via secrets 
      manager

KMS:
    - KMS hold keys that encrypt our data
    - Encryption process:
        1. Vault asks KMS: "give me a one-time data key"
        2. Vault encrypts your secret with that data key
        3. Vault stores: [encrypted secret] + [encrypted copy of data key]
        4. To read: vault asks KMS to decrypt the data key, then decrypts the secret

    - AWS managed keys:
        - created by aws
        - free of cost 
        - key policy: fixed by aws
        - no cross account sharing 
        - best for simple use cases 

    - Customer managed keys:
        - created by users
        - cost is 1 $ per month 
        - key policy: controlled by users
        - cross account sharing is possible

SSM Parameter store:
    - A hierarchical key-value store for configuration, which can also hold encrypted secrets.
    - parameter types:
        - String: plain text 
        - StringList: Comma-separated
        - SecureString: Encrypted with KMS

    # Create
    aws ssm put-parameter --name "/lab/app/api-key" \
      --value "abc123" --type SecureString

    # Read (decrypted)
    aws ssm get-parameter --name "/lab/app/api-key" --with-decryption

    # Read only the value
    aws ssm get-parameter --name "/lab/app/api-key" --with-decryption \
      --query Parameter.Value --output text

    # Read a whole branch
    aws ssm get-parameters-by-path --path "/lab/app" --recursive --with-decryption

    # Update
    aws ssm put-parameter --name "/lab/app/api-key" \
      --value "newvalue" --type SecureString --overwrite

    # History (versions)
    aws ssm get-parameter-history --name "/lab/app/api-key"

    - Permission required for your identity:
        {
            "Version": "2012-10-17",
            "Statement": [{
                "Effect": "Allow",
                "Action": [
                "ssm:GetParameter",
                "ssm:GetParameters",
                "ssm:GetParametersByPath"
                ],
                "Resource": [
                "arn:aws:ssm:REGION:ACCOUNT_ID:parameter/lab/app",
                "arn:aws:ssm:REGION:ACCOUNT_ID:parameter/lab/app/*"
                ]
            }]
        }

    - if parameter uses customer manager key, role also need kms:Decrypt on that key

Secrets Manager:
    - service built for secrets
    - provide encryption, versioning, automatic rotation,
        replication and fine-grained access control.

    - Max secret size is 64 KB
    - Encypted: with KMS (aws/secretsmanager by default, or your CMK)
    - Cost: $0.4 per secret per month + $0.05 per 10,000 API calls
    - Deletion: Has a recovery window of 7 to 30 days (default 30 days)
    - format: plain text or json

    # Create
    aws secretsmanager create-secret --name lab/db \
    --secret-string '{"username":"admin","password":"Pass#1"}'

    # Read
    aws secretsmanager get-secret-value --secret-id lab/db

    # Read only the secret text
    aws secretsmanager get-secret-value --secret-id lab/db \
    --query SecretString --output text

    # Add a new version
    aws secretsmanager put-secret-value --secret-id lab/db \
    --secret-string '{"username":"admin","password":"Pass#2"}

    # Delete (with recovery window)
    aws secretsmanager delete-secret --secret-id lab/db \
    --recovery-window-in-days 7

    # Undo a delete
    aws secretsmanager restore-secret --secret-id lab/db

    Version:
        - every time secret changes new version is created
        
        VersionStages:
            - also there is label for version stages 
            - AWSCURRENT, AWSPENDING, AWSPREVIOUS
            - pending is being tested, not yet live

        Rollback:
            aws secretsmanager update-secret-version-stage --secret-id lab/db \
                --version-stage AWSCURRENT \
                --move-to-version-id <OLD_VERSION_ID> \
                --remove-from-version-id <BAD_VERSION_ID>

    Note:
        - secret scheduled for deletion can't be read. 
          also we can't create another secret with same name 
          until it deleted completely after scheduled time.

    Permission:
        - It require below 2 permission to read the secret 
            1. secrets manger permission: secretsmanager:GetSecretValue
            2. KMS: kms:Decrypt
                - it required only for customer managed keys
        
    Least privilege policy for secret:
        {
            "Version": "2012-10-17",
            "Statement": [{
                "Effect": "Allow",
                "Action": "secretsmanager:GetSecretValue",
                "Resource": "arn:aws:secretsmanager:REGION:ACCOUNT_ID:secret:prod/shop/db-??????"
            }]
        }

    Least privilege policy for customer managed key:
        {
            "Effect": "Allow",
            "Action": "kms:Decrypt",
            "Resource": "arn:aws:kms:REGION:ACCOUNT_ID:key/KEY_ID",
            "Condition": {
                "StringEquals": {
                    "kms:ViaService": "secretsmanager.REGION.amazonaws.com"
                }
            }
        }

    Tag based access:
        {
            "Effect": "Allow",
            "Action": "secretsmanager:GetSecretValue",
            "Resource": "*",
            "Condition": {
                    "StringEquals": {
                    "secretsmanager:ResourceTag/app": "${aws:PrincipalTag/app}"
                }
            }
        }

    Deny request that comes from any vpc except specified vpc:
        - if we want to provide secret access to another account, we need cmk.
        - deny access unless request comes from specific vpc endpoint:
            {
                "Version": "2012-10-17",
                "Statement": [{
                        "Effect": "Deny",
                        "Principal": "*",
                        "Action": "secretsmanager:GetSecretValue",
                        "Resource": "*",
                        "Condition": {
                        "StringNotEquals": { "aws:SourceVpce": "vpce-0abc1234567890def" }
                    }
                }]
            }

Rotation:
    - if secret is leaked accidentally, it works until next rotation if rotation is configured.

    - How secret manager rotate secret?
        1. createSecret: Generate new password/secret value and store it as AWSPENDING
        2. setSecret: Changes the password in real database using lambda
        3. testSecret: Log in with new password to prove it works
        4. finishSecret: move AWSCURRENT to new version.

        Before:  v1 [AWSCURRENT]
        Step 1:  v1 [AWSCURRENT]   v2 [AWSPENDING]
        Step 2:  DB password now = v2's password
        Step 3:  test login with v2 → OK
        Step 4:  v1 [AWSPREVIOUS]  v2 [AWSCURRENT]

    Rotate secret in RDS:
        - for RDS, aws gives ready-made rotation lambda template, we need to pick schedule(every 30 days), 
          and secret manager does the rest

    Note:
        - where target supports role-based auth (s3, dynamodb, sqs, RDS) use the role and skip the secret. 
          role automatically rotate the credentials.
